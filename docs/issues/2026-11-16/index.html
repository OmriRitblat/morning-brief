Gadi Eisenkot, who holds the mandate to form a government, pledged a commission of inquiry and said Netanyahu should not remain in office. Yair Golan, Yair Lapid, Ahmad Tibi and the head of the Israel Bar Association called for an investigation.

Alibaba launches Qwen4-Max, its new top model, and cuts the price by a quarter

China's biggest cloud company says its new flagship does more work with fewer words, which is what actually sets the bill.

What happened
On Sunday Alibaba released Qwen4-Max, the new top model in its Qwen family, Reuters reported. Alibaba says it beats the previous flagship, Qwen3.8-Max from August, on complex professional and scientific work while using fewer tokens, and that it was trained with security checks to avoid writing vulnerable code. According to trade coverage of the launch, it can read up to 1 million tokens at once and costs $1.50 per million tokens going in and $4.50 per million coming out, down from $2 and $6. On Alibaba's own Work360 test, the company says the average cost of finishing a task fell from $4.43 to $1.67. The flagship is not downloadable; Alibaba says smaller open versions will follow.
What it means, in plain words
AI models are billed like a taxi meter that counts words: you pay for every chunk of text the model reads and writes. Those chunks are called tokens. There are two ways to make a ride cheaper: lower the price per kilometre, or take a shorter route. Alibaba says it did both: the price per token is 25% lower, and the model needs about half as many tokens to finish the same job, because it gets there with less back-and-forth. That is how a 25% price cut becomes, by Alibaba's count, a 62% cheaper task. Keep in mind that Work360 is Alibaba's own exam, and nobody outside has re-run it yet.
Why it matters and how it could be used
For companies that run AI agents all day, the number that matters is the cost of a finished job, not the sticker price per token. If Alibaba's claim holds up, a team could run the same overnight batch of, say, contract reviews or code fixes for roughly a third of the money. It also keeps price pressure on the American labs, and shows Chinese labs now publishing safety test results alongside new models.

Jargon, explained

Token
A chunk of text, roughly three-quarters of a word. Models read, write and are billed in tokens.
Context window
How much text the model can look at in one go. One million tokens is several thick books.
Open weights
The model's trained numbers are published, so anyone can download it and run it on their own machines.
Benchmark
A standard exam used to compare models. A company's own benchmark is like a student writing their own test.

Google DeepMind's AI agents write a 6.5-million-line proof that Signal's encryption code does what it promises

Instead of testing software and hoping, teams of AI agents produced a mathematical proof about the actual compiled program, and a simple, trusted checker confirmed it.

What happened
Google DeepMind published a technical report on AlphaProof Code, a system in which teams of 40 to 80 AI agents work for 24 to 72 hours on one machine to prove things about software. They pointed it at libsignal, the open-source library behind the Signal messenger's encryption, compiled for ARM processors on Linux. The agents produced about 6.5 million lines of proof showing that the handshake that starts a conversation and the 'ratchet' that keeps changing the keys have the security properties they are supposed to have. Humans wrote and approved about 26,000 lines stating what had to be proven. When the team put two old, already-fixed bugs back in, the proofs failed, as they should. DeepMind is explicit about limits: group chats, multiple devices and attackers with quantum computers are not covered, and it says this does not establish the security of the whole Signal app.
What it means, in plain words
Testing is like trying many keys in a lock and concluding it is probably safe. A formal proof is a mathematical argument that no key except the right one can ever open it. Such proofs are extremely tedious to write, so they are rare. The trick here is a division of labour. The AI agents do the tedious writing. A small, old-fashioned program called Lean then checks every step, and it accepts no hand-waving, so it does not matter if the AI is sometimes wrong: a wrong proof is simply rejected. And the proof is about the machine code, the final instructions the processor runs, not just the human-readable source, so a mistake introduced by the compiler would be caught too.
Why it matters and how it could be used
Proving real software correct has always cost too much human time to do widely. If agents can do the grind and a checker guarantees the result, proofs become affordable for the code everything else depends on: encryption libraries, operating-system kernels, and, closer to home, network drivers and protocol stacks. What humans still must get right is the short statement of what 'correct' means; a proof of the wrong statement is worthless.

Jargon, explained

Formal verification
Proving with mathematics that a program always behaves as specified, rather than testing some cases.
Lean
A programming language for writing mathematical proofs, with a small checker that confirms every step mechanically.
Machine code
The raw instructions the processor actually runs, produced from source code by a compiler.
Specification
The precise statement of what the program is supposed to do. The proof is only as good as this statement.
Ratchet
In Signal, a mechanism that changes the encryption key with every message, so stealing one key does not expose the rest.

Google opens /teamwork, its system for running teams of AI agents on research problems

The idea: many narrow agents plus an outside referee beat one big agent working alone.

What happened
Google Research described results from /teamwork, a feature of its Antigravity coding tool that runs many AI agents in parallel on one problem, and said outside scientists and developers can now use it with its Gemini 4 models. Google says 10,000 academic researchers can apply for six months of free top-tier access. Among the results Google claims, according to coverage of its post: a proof, together with university mathematicians, of an information-theory conjecture open since 2013, checked in Lean; 30 agents working out molecular structures from lab measurements with 95% exact matches, nearly double a single agent; and a rewrite of a video decoder in the Rust language that ended up 20 to 30% faster than the original. These are Google's own figures and have not been independently reproduced.
What it means, in plain words
A single AI agent on a long task is like one person trying to hold an entire project in their head: details blur, and nobody checks their work. /teamwork splits the job the way a company does. Each agent gets only the files and tools for its own step. Separate critic agents review the output without seeing how it was produced, so they cannot be talked into the same mistake. And wherever possible the final word goes to something that cannot be flattered: a proof checker, a test suite, a simulator, or a hardware counter that measures real speed.
Why it matters and how it could be used
It is the same lesson as the Signal story: AI output becomes trustworthy when something objective checks it. That tells you where agent teams are useful today, which is on problems with a clear referee, such as 'do all tests pass', 'is it faster', 'does the proof check'. A performance engineer could, for instance, let a team of agents try optimizations overnight and accept only those that pass the tests and measurably cut latency. Cost and failure rates were not published.

Multi-agent system
Several agents with different roles working on one task, such as builders, critics and a coordinator.
Verifier
An automatic check that says pass or fail, such as a test suite or a proof checker.
Conjecture
A mathematical statement believed to be true that nobody has yet proven.

The famous first picture of a black hole passes an independent re-check

A separate team rebuilt the image from the raw data with a different method, and the glowing ring is still there.

In 2019 the Event Horizon Telescope team published the first picture of a black hole: a blurry orange ring around a dark centre, in a galaxy called M87 about 55 million light-years away. The picture is not a photograph. It was computed from the signals of radio telescopes spread across the Earth, which together sample only scattered bits of the full image. Filling in the rest takes software and human choices, and at least one earlier study argued the ring might be a product of those choices rather than something real.

A team led by Samuel Lai, writing in Nature, has now redone the job a different way. First, instead of combining telescope signals in pairs, they combined them in groups of three, which makes errors caused by the air above each telescope and by the instruments cancel out. Second, they built an image-making AI that was trained only on everyday pictures such as cats, dogs and cars, so it had no idea what a black hole 'should' look like. They tested the method on shapes that were not rings and on other galaxies, froze it so nobody could tweak it afterwards, and only then ran it on the M87 data.

The ring came back, with the same size and tilt as in the original. It matches a black hole about 6.5 billion times the mass of the Sun. Finer details, such as how thick the ring is and where it is brightest, still differ between methods. This summary is based on Nature's news listing and the researchers' own account of their paper; the full news article is behind a login.

  1. What they found: an independent analysis of the original telescope data produces the same ring, with the same diameter and orientation, as the 2019 image.
  2. How: they combined telescope signals in threes so that local errors cancel, and used an image-making AI trained on ordinary photos, tested and locked before it ever saw the black hole data.
  3. Why it matters: one of the best-known results in modern science no longer rests on one team's methods, and the same approach could help other fields that build pictures from scattered sensors, such as medical scans and earthquake mapping.

Jargon, explained

Black hole shadow
The dark patch in the middle of the ring, where light falls into the black hole instead of reaching us.
Light-year
The distance light travels in a year, about 9.5 trillion kilometres.
Closure invariant
A quantity made by combining signals from three telescopes so that each telescope's own errors cancel out.
Solar mass
The mass of our Sun, used as a measuring unit for stars and black holes.

Completion queues: how the card says the work is done

Monday track: RDMA and NICs

The big idea: An RDMA network card does your requests in the background, so it needs a way to report back. For every finished job it writes a short receipt into a list in memory that your program can read directly, without asking the operating system.

First, the basics

Quick recap of where we are. With RDMA, a program hands work straight to the network card. It does this through a queue pair, which is a send queue plus a receive queue belonging to one connection. Each item you put in is a work request: one instruction such as 'send these bytes' or 'here is an empty buffer for whatever arrives next'. The important detail is that posting a work request is asynchronous: the call returns immediately, before the card has done anything. It is like dropping clothes at the dry cleaner. You walk out right away, and the cleaning happens later.

That leaves two questions: is my job finished, and did it succeed? The answer to both is the completion queue, or CQ. A CQ is a ring, meaning a fixed-size array used in a circle, that sits in memory shared between the card and your program. Each time the card finishes a work request it writes one entry there. The entry is called a completion (a 'work completion' in the programming interface, a CQE in hardware documents). It is the receipt: which job, success or failure, how many bytes.

There are two ways to find out that a new receipt has arrived. Polling means your program simply looks at the queue again and again. Events mean you ask the card to raise an interrupt, a hardware signal that makes the CPU stop what it is doing and run operating-system code, which then wakes your sleeping program. Polling reacts fastest but keeps a CPU core busy. Events cost nothing while idle but add a delay each time.

How it works, step by step
  1. Create the queue. The program calls ibv_create_cq and asks for a capacity, for example 4,096 entries. When it later creates each queue pair, it names which CQ gets its send receipts and which gets its receive receipts. They can be the same one, and many queue pairs can share a single CQ.
  2. Post work with a name tag. Every work request carries wr_id, a 64-bit number that you choose and the card never interprets. Programs usually put a pointer or an index to their own record of the buffer there. The post call returns immediately.
  3. The card does the work. For a send on a reliable connection, it transmits the data and waits for the other card's acknowledgment. For a receive, it takes the next buffer you supplied and writes the arriving message into it.
  4. The card writes the receipt. It fills the next free slot of the CQ, 64 bytes on ConnectX cards, with the status, the type of operation, the byte count and the queue pair number, and flips an ownership bit in the slot so software can tell this entry is new.
  5. The program polls. It calls ibv_poll_cq(cq, 16, array), meaning 'give me up to 16 receipts'. The library, running inside your own process, looks at the next slot in shared memory. No system call happens. It returns how many it found (zero if none) and fills in a small structure for each, with wr_id, status, opcode, byte_len and qp_num.
  6. Act on each receipt, status first. On success, a send receipt means you may reuse that buffer; a receive receipt means byte_len bytes of data are waiting in the buffer you named, and you should post a fresh empty buffer to replace it. On failure, only a few fields can be trusted (wr_id, status, the queue pair number and a vendor error code), and the connection has moved to an error state.
  7. When idle, go to sleep safely. Call ibv_req_notify_cq to arm the CQ, poll one more time, and only if it is still empty block in ibv_get_cq_event. At the next completion the card raises one interrupt and the kernel wakes you. The arming is one-shot, so you re-arm each time.
A practical example
Picture a web server running on XLIO and calling recv() on a connection. Inside that call, XLIO polls the receive completion queue of its ring, taking up to 16 completions per look (XLIO_CQ_POLL_BATCH_MAX, default 16). Each completion points to a packet that the card has already written into XLIO's memory. XLIO runs those packets through its own TCP code, and if data for this socket is ready, recv() returns it. No system call, no interrupt, no context switch. If nothing has arrived, XLIO keeps looking, up to 100,000 times by default (XLIO_RX_POLL), and only then arms the queue and sleeps in the kernel until the card interrupts. While it sleeps, interrupt moderation makes the card wait until 48 packets have gathered or 50 microseconds have passed before waking it (the defaults), so a burst costs one wake-up instead of dozens.
Why it matters for XLIO
The heart of XLIO's fast path is a loop that polls completion queues from user space. Received packets, finished sends and the return of send buffers all show up as completions, and XLIO reads the ConnectX completion entries straight from shared memory. The polling knobs you see in XLIO tuning guides (how long to poll before sleeping, how many completions per poll, interrupt moderation) are all decisions about this one queue: spend CPU to get the lowest latency, or give up some latency to save CPU.

Common misconception
Misconception: a successful send completion means the other application got my message. It does not. On a reliable connection it means the remote card acknowledged the data and placed it in the receiver's buffer. The remote program may be busy, or stuck, and may not have looked yet. On an unreliable datagram connection it means even less: only that the packet left your card. If you need to know the other program processed the message, it has to send a reply. A related tradeoff: you can ask the card to skip receipts for most sends to save work, but then send-queue slots are only freed when a later signalled send completes, so you must still request a receipt every so often or the send queue fills up.

Jargon, explained

RDMA
Remote direct memory access: the network card moves data directly between the memory of two machines, with little or no operating-system involvement.
Queue pair (QP)
A send queue plus a receive queue: the RDMA equivalent of one end of a connection.
Work request
One instruction to the card, such as 'send this buffer' or 'use this buffer for the next arrival'.
Completion queue (CQ)
A ring in shared memory where the card writes one receipt for each finished work request.
Completion (CQE)
One receipt in the completion queue: which job, whether it succeeded, how many bytes.
Polling
Checking for new completions yourself, repeatedly, instead of waiting to be told.
Interrupt
A hardware signal that makes the CPU stop and run operating-system code to handle an event.
System call
A request from a program to the operating system. It costs time because the CPU has to switch into the kernel and back.
Interrupt moderation
Making the card hold back an interrupt until several packets have arrived or a short time has passed.
Self-test: Your program polls the completion queue, finds it empty, arms it for an interrupt and goes to sleep. Once in a while it stays asleep even though a completion is sitting in the queue. What happened, and what is the fix?

The completion arrived in the tiny gap after the last poll and before the arming. Arming only produces an interrupt for completions that arrive after it, so this one never triggers a wake-up. The fix is the order: arm first, then poll once more, and sleep only if that poll is also empty. Anything that slipped into the gap is caught by the extra poll, and anything later triggers the interrupt.
